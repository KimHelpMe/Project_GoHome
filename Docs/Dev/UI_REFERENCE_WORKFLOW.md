# GoHome UI Reference Pack 워크플로우

> UI를 곧바로 UMG에서 시행착오로 만들지 않는다. 먼저 **UI Reference Pack**으로 화면의 상태·입력·전환·모션을 합의하고, 그 계약을 기준으로 Unreal 구현과 검증을 진행한다. **이 절차 문서 자체는 팀 공유 md/git이지만, Pack 산출물(`Docs/Dev/UI/<screen>/`)은 개인 작업 영역이다** — `.gitignore`로 제외되어 Git에 올라가지 않는다. 이 문서는 Claude Code와 Codex 양쪽에서 동일하게 동작하도록 만든 **개인 환경 세팅**이며, 다른 팀원에게 강제하는 절차가 아니다. 팀원 각자 필요하면 이 문서를 참고해 자기 개인 Pack을 두면 된다.

## 역할과 경계

- [UI_GUIDE.md](UI_GUIDE.md)는 UI 레이어·소유자·데이터 흐름·라우터·UMG 연출 배치의 **구조 규칙** 단일 출처다.
- 이 문서는 화면 하나의 시각적 방향과 상호작용을 구현 전에 구체화하는 **참조 계약**의 절차와 형식을 정한다.
- 게임의 의도, UX 목표, 밸런스 근거는 Notion이 출처다. Reference Pack은 그 결정을 대체하거나 새로 발명하지 않는다.
- `Content/GoHome/UI/`의 위젯과 관련 코드가 구현 현황의 단일 출처다. Pack에 “구현 완료/미완료” 상태표를 남기지 않는다.

## 언제 만드는가

다음 중 하나면 구현 전에 Pack을 만든다.

- 신규 HUD, Modal, Fullscreen/Sequence, System 화면
- 기존 화면의 레이아웃·사용자 흐름·입력 방식·모션을 바꾸는 작업
- 화면 전환, 로딩, 정산처럼 여러 상태가 시간 순서로 이어지는 작업

색상 하나, 문구 하나, 기존 위젯의 명백한 버그를 고치는 일에는 만들지 않는다. 기존 Pack을 바꾸는 시각적 결정이면 해당 Pack만 갱신한다.

## 화면별 파일 구조

새 Pack은 아래 경로에 화면군 단위로 둔다(`Docs/Dev/UI/`는 `.gitignore` 대상 — 로컬에만 존재). `<screen>`은 UMG 폴더와 같은 kebab-case 이름을 쓴다.

```text
Docs/Dev/UI/<screen>/
  README.md             # 승인된 화면 계약의 진입점
  prototype.html        # 클릭 가능한 레이아웃·상태·모션 참조
  motion.md             # 시간, easing, 중단/스킵 규칙
  implementation.md     # Pack ↔ UMG/BP/데이터 연결 매핑
```

- `prototype.html`은 정적 목업이 아니라 상태를 직접 전환해 볼 수 있는 참조 구현이다. 실제 게임 데이터·네트워크·외부 리소스에 접속하지 않는다.
- 무드보드·일러스트·아이콘 후보는 필요할 때만 `references/` 아래에 둔다. 대용량 원본과 반복 스크린샷은 보관하지 않고, 구현 판단에 필요한 최종 비교 캡처만 작게 보관한다.
- 공용 디자인 토큰이 생기면 화면별로 복사하지 않고 `Docs/Dev/UI/DESIGN_TOKENS.md`를 새로 만들고 Pack에서 링크한다. 아직 토큰 파일은 만들지 않는다.

## Reference Pack 작성 순서

### 1. Brief를 확정한다

`README.md` 맨 앞에는 아래만 짧게 적는다.

- 화면의 목적과 성공 조건
- 진입 조건과 종료 조건
- 대상 레이어 및 소유자 (`UI_GUIDE.md`의 카탈로그와 일치)
- 사용자 입력과 접근성/게임패드 고려 사항
- 필요한 데이터와, 데이터가 없거나 갱신 중일 때 보이는 상태
- 의도적으로 제외한 범위

미정인 시각적 방향은 확정 사실처럼 쓰지 않는다. 에이전트는 기존 UI와 Notion 근거로 2~3개의 후보를 만들 수 있지만, 방향 선택이 필요한 경우 사람의 승인을 받기 전에는 그것을 구현 계약으로 승격하지 않는다.

### 2. 상태와 흐름을 먼저 정한다

`README.md`에 정상 상태만 그리지 말고 다음을 표로 적는다.

| 상태 | 진입 조건 | 사용자 입력 | 표시/입력 규칙 | 다음 상태 |
|---|---|---|---|---|
| 예: Loading | 데이터 요청 시작 | 취소 불가 | Skeleton 표시, 입력 잠금 | Ready / Error |

필수 고려 대상: initial, loading, empty, ready, selected, disabled, error, close/exit. 해당 화면에 맞지 않는 상태는 제외 이유를 적는다. 화면 간 순서가 핵심이면 Mermaid 흐름도를 `README.md`에 추가한다.

### 3. 프로토타입으로 동작을 확인한다

`prototype.html`은 적어도 첫 화면과 핵심 상호작용 하나, 로딩 또는 오류 상태 하나, 열림/닫힘 전환을 보여 준다.

- 이미지 생성물은 분위기 참조용이며 레이아웃·입력·모션의 유일한 근거가 될 수 없다.
- 프로토타입에서 확인한 상태 이름은 Unreal 위젯/BP의 상태 이름과 가능한 한 맞춘다.
- 마우스 hover만으로 필수 정보를 숨기지 않는다. 키보드/게임패드 포커스와 reduced-motion 대안을 명시한다.

### 4. 모션을 숫자로 계약한다

`motion.md`에는 “부드럽게” 같은 표현 대신 다음을 적는다.

효과 후보와 조합 방식을 찾을 때는 [UI_MOTION_CATALOG.md](UI_MOTION_CATALOG.md)의 의미 패턴과 레시피를 참고한다. 카탈로그는 후보 탐색용이며, 실제 재생 시점과 조합은 해당 `prototype.html`에서 확인한 뒤 화면 계약에 적는다.

| 전환 | 시작 → 끝 | 시간 | easing | 입력/중단 규칙 | Unreal 소유자 |
|---|---|---:|---|---|---|
| 예: Modal Open | opacity 0→1, scale 0.96→1 | 180ms | ease-out | 끝날 때까지 뒤 UI 입력 차단 | 위젯 UMG Animation |

- 화면 내부의 순차 연출은 해당 위젯이 소유한다.
- 화면 간 전환은 `UI_GUIDE.md`의 상위 레이어/라우터가 소유한다.
- 스킵 가능 여부, 재진입 시 처리, 네트워크 결과가 애니메이션 중 도착할 때의 처리도 적는다.
- `prefers-reduced-motion`에 해당하는 참조 동작(즉시 표시 또는 짧은 fade)을 정한다. Unreal에서는 프로젝트 접근성 정책에 맞춰 동등한 옵션으로 구현한다.
- `motion.md`는 레퍼런스에서 확인된 효과의 트리거·순서·시간을 계약한다. 문서에 적혀 있다는 이유만으로 레퍼런스에 보이지 않는 효과를 추가하지 않는다. 효과를 연결하기 전에 실제 프로토타입의 해당 상태와 재생 시점을 열어 확인하고, 각 효과의 근거(확인한 화면/시점 또는 사용자의 명시 지시)를 기록한다. 구현 후에는 같은 상태의 전체 화면에서 일시 효과의 활성 프레임과 정착 프레임을 모두 확인한다.

### 5. Unreal 구현으로 매핑한다

`implementation.md`에는 시안 요소마다 이름을 새로 발명하지 말고 실제 대상만 매핑한다.

| 참조 요소/상태 | UMG Widget/BP | 데이터·이벤트 | 구현 방식 | 검증 관찰점 |
|---|---|---|---|---|
| 예: Confirm 버튼 disabled | `WBP_ZoneSelect` | Zone 유효성 | Widget BP | 무효 선택에서 포커스/클릭 불가 |

새 위젯·DataAsset·이벤트가 필요하면 먼저 `UI_GUIDE.md` 및 `ARCHITECTURE.md`의 경계에 맞는지 확인한다. Pack은 C++/Blueprint 경계를 바꾸는 권한이 아니다.

## 승인과 구현 게이트

Reference Pack은 다음 두 단계로 쓴다.

1. **후보 작성**: 에이전트가 프로토타입과 명세 초안을 제시한다. 이 단계에서는 구현용 `.uasset`를 만들거나 기존 UI의 시각적 방향을 바꾸지 않는다.
2. **방향 승인 후 구현**: 사람이 특정 후보 또는 수정 지시를 승인하면, 해당 Pack을 정리해 구현 계약으로 삼고 UMG/BP를 수정한다.

이미 승인된 Pack의 명백한 구현 누락·버그 수정은 재승인 없이 처리할 수 있다. 그러나 레이아웃, 정보 우선순위, 입력 흐름, 모션 의미를 바꾸면 Pack과 함께 다시 검토한다.

## 에이전트 협업 모델

사람이 모든 시안을 직접 만들 필요는 없다. 다만 에이전트 여러 명이 같은 결정을 반복하거나, 한 에이전트가 자기 결과를 자기 기준으로 승인하게 만들지 않는다. 아래 역할을 **순서대로 한 번씩** 호출한다. 한 에이전트가 여러 역할을 맡을 수 있지만, 산출물과 검토 관점은 분리한다.

Claude Code에서는 `/ui-reference-pack [draft|implement|review] [화면 또는 기능]` 로컬 스킬로 이 절차를 실행할 수 있다. Codex의 같은 이름의 로컬 스킬도 Claude 스킬 원본을 읽도록 연결한다. 스킬과 화면별 Pack 산출물은 전부 개인 환경에만 두며(둘 다 `.gitignore` 대상), Git에 추적되는 공통 자산은 이 절차 문서 하나뿐이다.

| 역할 | 입력 | 책임 산출물 | 하지 않는 일 |
|---|---|---|---|
| UI 기획 에이전트 | 게임 의도, 사용자 요구, 기존 UI/Notion 근거 | `README.md`의 목적·사용자 흐름·상태·입력·수용 기준 | 근거 없는 미술 방향 확정, UMG 구현 |
| UI 디자인 에이전트 | 승인 대기 중인 brief, 기존 UI의 스타일·제약 | `prototype.html`, `motion.md`의 2~3개 방향 또는 요구된 단일 방향 | 게임 데이터 계약 변경, 코드·에셋 수정 |
| 구현 에이전트 | 승인된 Pack, `UI_GUIDE.md`, 관련 코드/위젯 | `implementation.md` 매핑, UMG/BP 구현, 빌드·PIE 검증 | 승인되지 않은 시각/흐름 결정을 묵시적으로 확정 |
| UI 검토 에이전트 | 승인된 Pack, 실제 에디터 화면/로그/입력 결과 | Pack 대비 차이, 접근성·상태 누락·모션 문제의 우선순위 리뷰 | 새 디자인 방향을 독단적으로 승인, 자기 리뷰만으로 구현 종료 |

### 역할 사이의 핸드오프

1. **기획 → 디자인**: 기획 에이전트는 요구를 화면 목적, 상태 전이, 수용 기준으로 바꾼다. 모호한 게임 의도나 수치는 Notion 근거를 사람에게 받아야 하며 스스로 채우지 않는다.
2. **디자인 → 사람 승인**: 디자인 에이전트는 같은 사용자 흐름을 유지한 후보만 제시한다. 후보 비교는 정보 우선순위, 조작 비용, 게임 분위기, 구현 위험을 짧게 설명한다. 사람은 후보 선택·수정·보류 중 하나를 결정한다.
3. **승인 → 구현**: 사람의 선택을 `README.md`의 `결정` 절에 한 문장으로 기록한 뒤에만 구현 에이전트가 실제 UI를 변경한다. 이 결정은 구현 상태표가 아니라 디자인 계약이므로 구현이 끝난 뒤에도 남긴다.
4. **구현 → 독립 검토**: UI 검토 에이전트는 구현 에이전트와 다른 컨텍스트에서 Pack과 실제 화면을 비교한다. 한 차례 검토로 끝내며, P0/P1 문제 또는 승인된 계약과의 의미 있는 차이만 재작업으로 보낸다.

### 반복과 비용 제한

- 기본값은 **기획 1회 → 디자인 1회 → 사람 승인 → 구현 1회 → 독립 검토 1회**다.
- P0/P1 결함 또는 사람이 새 방향을 요청한 경우에만 디자인/구현 단계를 다시 연다. “더 예쁜 대안”만을 이유로 자율 반복하지 않는다.
- 디자인 후보는 기본 2개, 최대 3개다. 이미 스타일 기준이 확정된 화면은 단일 후보만 만든다.
- 리뷰 에이전트는 수정 권고와 근거를 보고하지만, 다른 에이전트의 Git 변경을 되돌리거나 승인된 Pack을 임의로 대체하지 않는다.

### 사람 승인 없이 자동 진행할 수 있는 범위

기존에 승인된 Pack을 정확히 따르는 마크업/UMG 작성, 컴파일 오류 수정, 누락된 상태 구현, 접근성·입력 버그 수정, Pack과 일치하는 모션 수치 적용은 자동 진행할 수 있다. 화면의 시각적 방향·정보 우선순위·사용자 흐름이 달라지는 경우만 사람이 결정한다. 이 경계가 무인 구현의 속도와 디자인 책임의 균형점이다.

## 에이전트 작업 규칙

Claude Code와 Codex 모두 UI 작업을 받으면 다음 순서를 따른다. 역할형 작업이면 바로 위 에이전트 협업 모델의 해당 역할과 산출물 범위를 먼저 적용한다.

1. [UI_GUIDE.md](UI_GUIDE.md), 관련 `ARCHITECTURE.md` UI 절, 해당 화면 Pack이 있으면 그 Pack을 읽는다.
2. Pack이 없고 위 “언제 만드는가”에 해당하면 구현 전에 Pack 초안을 만든다.
3. 승인된 Pack이 있으면 `implementation.md`의 검증 관찰점을 완료 조건으로 사용한다.
4. UMG/BP 변경 후 컴파일/에디터 로드와 핵심 상태 전환을 확인한다. 가능하면 PIE에서 실제 입력 경로도 검증한다.
5. 구현과 Pack이 달라지면 조용히 한쪽만 바꾸지 않는다. 변경 이유를 제시하고 승인된 방향에 맞춰 둘을 함께 갱신한다.

## 검토 기준

구현 전에는 다음을 확인한다.

- 첫 1초에 사용자가 무엇을 해야 하는지 알 수 있는가
- 로딩·빈 상태·오류 상태가 빠지지 않았는가
- 마우스뿐 아니라 키보드/게임패드에서도 핵심 흐름이 가능한가
- 시간 기반 연출에 입력 잠금, 취소, 재진입 규칙이 있는가
- `UI_GUIDE.md`의 레이어·소유자·라우터 원칙과 충돌하지 않는가
